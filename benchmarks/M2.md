# Apple M2でのVOICEVOX / LiteVox性能測定

VOICEVOX 0.25.2とC++ native LiteVoxを、同じモデル・クエリ・出力形式で比較した。
CPU同士の波形生成速度はほぼ同等だった。
Metal/WebGPUを使うLiteVoxは、CPU各1スレッドの比較で短文読み上げが約5.4倍、歌唱が約4.2倍速かった。
これは測定した短い入力と設定での結果であり、本家の最速設定に対して常にこの倍率になるという意味ではない。

[生データ・入力・ハッシュ](M2.json)と[測定スクリプト](../tools/Benchmark.py)を同梱している。

## 条件

- Apple M2、CPU 4性能コア＋4効率コア、GPU 8コア、メモリ16GiB、macOS 26.5.2。
- 同一の公式配布モデル、辞書を参照。読み上げ3は `0.vvm`、歌唱教師6000 / 歌唱3000は `s0.vvm` に含まれることをVVMメタデータで確認。両モデルと両ORTライブラリのSHA-256は生データに保存。
- 本家とCPU基準のLiteVoxは、配布同梱VOICEVOX ONNX Runtime 1.17.3。GPU版と新ランタイムCPU対照はMicrosoft ONNX Runtime 1.30.0。
- 読み上げスタイル3、テキスト「こんにちは。」。歌唱教師6000、歌唱スタイル3000、165フレームの同一スコア。
- 24kHz、モノラル、16bit PCM。読み上げ1.056秒、歌唱1.760秒のWAV。
- 本家が作ったクエリの同一バイト列を双方へ送信。保存したリクエストSHA-256と、全条件のWAV形状が一致することを確認。
- HTTP POST、新しい接続、全レスポンス受信までの時間。worker 1、同時リクエストなし。
- 各操作の初回と追加2回のウォームアップを除き、5回測定した中央値。本家→LiteVox / LiteVox→本家の順序を交互にした。
- 初回値も保存しているが、参照クエリの作成で本家の一部モデルが暖まるため、公平なコールドスタート比較には使わない。

## CPU同士：同じORT、各1スレッド

| 操作 | 本家 | LiteVox native CPU |
|---|---:|---:|
| 読み上げクエリ | 1.751 ms | 1.257 ms |
| 読み上げ波形生成 | 1,377.917 ms | 1,391.719 ms |
| 歌唱クエリ | 24.811 ms | 27.408 ms |
| 歌唱波形生成 | 825.234 ms | 820.750 ms |

波形生成に大きなCPU速度差はない。
C++化だけでニューラルモデルの計算自体が速くなるわけではなく、同じORT・モデルを使う部分の計算量は同じである。

## Metal/GPU：CPU各1スレッド

| 操作 | 本家 CPU | LiteVox Metal | 波形生成の倍率 |
|---|---:|---:|---:|
| 読み上げクエリ | 1.434 ms | 1.073 ms | — |
| 読み上げ波形生成 | 1,432.329 ms | 263.300 ms | 5.44倍 |
| 歌唱クエリ | 26.517 ms | 25.502 ms | — |
| 歌唱波形生成 | 884.231 ms | 211.058 ms | 4.19倍 |

波形生成のRTF（生成秒数÷音声秒数）は、読み上げ0.249、歌唱0.120だった。
GPU版は音長・音高・歌唱教師をCPUに、重い波形デコーダをGPUに置く。
小さな予測モデルまでGPUへ送る固定費を避ける構成であり、全演算がGPUで動くという意味ではない。

新しいORTのCPU対照では、読み上げ波形が本家1,293.773 ms / LiteVox 1,301.179 ms、歌唱波形が797.791 ms / 793.096 msだった。
CPU対照がほぼ同等であることから、上記のGPU結果をランタイム更新だけの効果とは扱わない。
ただし対照とGPU比較は別の試行であり、更新の寄与を厳密に分離した演算単位の実験ではない。

## CPUスレッド数も重要

| CPUスレッド数 | 本家：読み上げ | native CPU：読み上げ | 本家：歌唱 | native CPU：歌唱 |
|---|---:|---:|---:|---:|
| 1 | 1,377.917 ms | 1,391.719 ms | 825.234 ms | 820.750 ms |
| 4 | 410.915 ms | 387.426 ms | 258.083 ms | 279.161 ms |
| 0：ORT既定 | 678.084 ms | 719.055 ms | 623.895 ms | 566.817 ms |

この機械と入力では、測定したCPU設定の中で4スレッドが最も速かった。
`0`で全物理コアの既定値に任せるより、明示した4の方が良かった。
CPUならまず `--cpu-threads 4`、Metalなら `--cpu-threads 1 --gpu` を比較する。
最適値は機械・入力長・同時接続数・バックグラウンド負荷に依存するため、既存の `0` の意味は変更していない。

CPU4の最速観測値とGPUの主比較値は別試行なので、その比を公平な直接比較の倍率としては示さない。
CPU4本家とGPU1 LiteVoxを同居させた追加の交互試行も保存したが、本家の波形時間が1,863.170 / 1,541.925 msに増加した。
共有ホストの負荷・スレッドプール・メモリ状況への感度が大きく、「CPU4を最適化してもGPUが7倍速い」とは結論しない。

## GPUが実際に使われた根拠

nativeの実モデルで読み上げと歌唱のCLI生成が成功し、非無音PCMと期待するWAV形状を確認した。
ORTの詳細ログでは歌唱デコーダの612ノードが `WebGpuExecutionProvider`、360ノードがCPUに配置されていた。
GPUのモデル作成・実行が失敗した場合に、別のCPUライブラリへ黙って切り替える経路は禁止している。
providerが一覧に出ることや `gpu_mode=true` だけを成功の根拠にはしていない。

native WebGPUはDawnを使い、macOSではAppleのMetalに接続する。
参照：[公式WebGPU EP文書](https://onnxruntime.ai/docs/execution-providers/WebGPU-ExecutionProvider.html)。

CoreMLも、C API位置の修正、MLProgram、`MLComputeUnits=ALL`、動的形状、compute planの確認まで実行した。
しかしORT 1.30.0では、このモデルの中間出力309の形状を解決できず、波形モデル作成が失敗した。
エラーは `RegisterModelInputOutput Unable to get shape for output: 309`。
CoreMLでの生成成功・高速化は主張せず、Macでは動作確認済みのWebGPUを優先する。
参照：[公式CoreML EP文書](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html)。

WindowsのCUDA / DirectML、LinuxのCUDA / Vulkan-WebGPUの選択経路は実装したが、このMacで実機検証はできない。
DirectMLには高性能GPU選択、sequential mode、memory pattern無効化、共有セッションのRun排他制御を適用した。
参照：[公式DirectML EP文書](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)。

## 再測定

公式エンジンとLiteVoxは同じモデル・辞書を参照させ、書き込み状態は別ディレクトリにする。
GPUプロファイルのログ出力は、速度測定時には無効にする。

```sh
# 保存した入力を復元する
mkdir -p build
python3 - <<'PY'
import json
from pathlib import Path
Data = json.loads(Path('benchmarks/M2.json').read_text())
Path('build/Score.json').write_text(json.dumps(Data['score'], ensure_ascii=False))
PY

# 公式エンジンの展開ディレクトリで起動：状態保存先は専用の絶対パス
HOME=/absolute/path/to/official-state \
XDG_DATA_HOME=/absolute/path/to/official-state \
./run --host 127.0.0.1 --port 50121 --cpu_num_threads 1

# 別ターミナル：標準ORT＋Metal、元のVV-BIN変換用ライブラリも残す
LITEVOX_VV_BIN_ONNXRUNTIME=/path/to/runtime/libvoicevox_onnxruntime.dylib \
dist/litevox server --runtime /path/to/runtime \
  --onnxruntime /path/to/onnxruntime/lib/libonnxruntime.dylib \
  --state-dir build/bench-native-state --port 50123 \
  --workers 1 --cpu-threads 1 --gpu

# 同一入力を再送し、両エンジンを交互に測定する
python3 tools/Benchmark.py \
  --engine official=http://127.0.0.1:50121 \
  --engine litevox=http://127.0.0.1:50123 \
  --score build/Score.json --replay benchmarks/M2.json \
  --case talk-short --case song --runs 5 --out build/result.json
```

CPU対照はLiteVoxを `--acceleration-mode cpu` にし、同梱ORT / 標準ORTをそれぞれ指定する。
1、4、0の比較では双方のCPUスレッド数を揃える。
長文や同時リクエストは、必要な利用条件に合わせて別に測定する。

## 回帰確認

- `make check dist`：既存JSON・歌唱・SoXRと、provider選択・CPU予測/GPUデコーダ分離のチェックが成功。
- [CLI smoke](../tools/verify-cli-smoke.sh)：読み上げ、歌唱、ストリーミング、44.1kHzステレオ、スコア拒否、CLI/HTTP連携が成功。
- [公式HTTP比較](../tools/compare_voicevox_http_full.py)：双方の新しい状態保存先で、Metal版との65ケースすべてが成功。辞書・プリセット・設定の更新も含む。
- 2 workerのMetalサーバーへ6件の並行合成を送り、全応答のPCM・フレーム数・非無音を確認。

## 限界

これは他の作業も走る対話用Macでの短い実測で、専有機の最大性能測定ではない。
最初の長文・複数エンジン測定は別の重いPython処理と約7GiBのswapを確認したため中断し、主結果には採用していない。
その後に入力を固定した交互試行へ切り替えたが、試行間のバックグラウンド負荷や温度は完全には固定できない。
全入力・全OS・全GPUでの最高速度や、GPU版のビット単位のCPU一致は保証していない。
WAVの形状一致・非無音・API互換性と、providerへの実演算配置を別々に検証する。
